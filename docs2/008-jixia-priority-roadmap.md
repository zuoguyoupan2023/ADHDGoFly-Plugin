### 当前判断与下一步

正文图片筛选器第一阶段已经完成并接入“发现网页图片”流程。这里的“接入”是指：用户点击现有的“发现网页图片”按钮后，系统先扫描选区或全文中的 `<img>`，再运行筛选器，最后只把筛选后保留的图片放入图像工作区；图像工作区、GLM 识别队列和 Chat 合并逻辑不变。筛选器不是独立的第二个入口，也不会自动上传或识别图片。

当前最应该做的是 **截图兜底的智能定位**，作为图片发现链路的第二阶段收尾：

1. 图片 URL 下载失败或无法读取时，定位该图片 DOM 在页面中的位置。
2. 必要时滚动到目标图片，使目标进入视口。
3. 截取目标图片附近区域，而不是无条件截取当前视窗。
4. 将截图标记为 `delivery: "screenshot"`，保留原图片 URL、定位信息和失败原因，并继续进入同一个图像工作区。

筛选器解决“候选太多、质量太差”，智能截图解决“正文图片留下了但无法下载”；工作区和历史管理则解决“图片处理后无法整理、导出和清理”的问题。下一阶段优先做历史搜索/按时间清理和批量导出，再进入官方模型清单维护与视觉模型适配验证。

### 剩余任务的主次判断

按“先完成主功能，再补细节”的原则，当前剩余任务分为两层：

**后续细节/可暂缓：**

- 全供应商模型清单、预告模型维护和复杂能力矩阵。

- 云端 TTS、语音生成/克隆以及图像生成。

### Kimi K3 真实验收方案

本章节是 K3 从“代码已接入”变成“功能已验收”的唯一标准。验收使用 Chat 输入框 `+` 直接添加原图，选择 Moonshot / `kimi-k3`，优先使用“图片+识别结果”模式；测试时不得把 GLM-4V-Flash 识别结果当作 K3 原图理解能力的证明。

#### 用例 A：单图理解

- 输入：一张普通新闻图、截图或页面配图。
- 问题：`请直接观察原图，描述主体、场景、布局、关键文字和不确定之处。`
- 通过标准：K3 回复明确引用原图可见信息；至少覆盖主体、布局和一项图中文字/视觉关系；不能只复述 GLM 文本。

#### 用例 B：图片 + 正文联合理解

- 输入：先添加当前文章全文，再通过 Chat `+` 添加一张与文章相关的图片。
- 问题：`结合正文和原图回答：图片支持正文中的哪些观点？哪些信息只存在于图片中？`
- 通过标准：回复同时引用正文和图片证据，能区分两者来源；若图片与正文不一致，明确指出不一致，而不是强行合并。

#### 用例 C：图表/论文图片理解

- 输入：一张柱状图、折线图、表格或论文 Figure。
- 问题：`说明横纵轴、单位、图例、主要趋势、异常点和不能确定的信息；不要编造缺失数值。`
- 通过标准：能读出图表结构和趋势；区分精确读数与估计值；缺少单位、图例或数据时明确说明；不因图片模糊而给出确定性幻觉。

#### 用例 D：错误降级

依次验证无效 Key、超时/断网、图片过大或不支持格式。

- 通过标准：显示可读错误；不显示“已识别”或伪造结果；原图仍留在 Chat/工作区，可重试或改用 GLM-4V-Flash；普通文本 Chat 不被破坏。

#### 验收记录

每个用例登记：日期、provider、model、图片来源、请求模式、结果摘要、失败原因和是否通过。四个用例全部通过后，才把 K3 状态从“进行中”改为“已验证”；未通过时只修复请求/状态边界，不扩展新模型。

### 多模态模型与非多模态模型使用流程

模型是否支持视觉必须按模型能力登记表判断，不能因为供应商名称相同就默认支持图片。

| 模型类型 | 图片发送方式 | 是否需要 GLM-4V-Flash | 结果进入 Chat 的内容 |
|---|---|---:|---|
| 原生视觉模型，如 Kimi K3、已验证的 GPT/Claude/Gemini 视觉模型 | 原图，必要时附识别结果 | 否；用户可选择并行识别 | 原图 + 模型回答，视觉回答另存图像历史 |
| 视觉能力已声明但尚未实测的模型 | 暂按识别结果或受控灰度 | 是 | 识别结果，禁止默认发送原图 |
| 纯文本模型 | 不发送原图 | 是 | GLM OCR/视觉结果文本 |

非多模态模型的流程固定为：`添加图片 → GLM-4V-Flash 识别/OCR → 用户确认结果 → 识别文本进入 Chat → 原图不上传给纯文本模型`。如果 GLM 失败，保留图片和错误状态，不伪装成文本上下文。

### P4：后置能力（均未完成）

P4 表示不影响当前网页图片理解主闭环的后置任务，保留完整设计细节，但不作为近期验收条件：

- 音频文件转写、云端 TTS、语音生成/克隆。
- 原生多图一次请求、视频视觉模型和视频上传/抽帧适配。
- 全供应商模型能力矩阵、预告模型维护和复杂能力自动同步。
- 信息图、数据图表、关系图、时间线及可编辑视觉结果。

## 一、总架构逻辑

```text
网页 / 选区 / 图片 / 音频 / 词典 / 测试历史
                    ↓
             JixiaContext
                    ↓
       任务选择 + 能力/预算/权限检查
                    ↓
              JixiaTask
                    ↓
       结构化结果 + 原文/媒体证据
                    ↓
          用户确认、修改、复习、导出
```

所有任务都应声明：

- 支持的上下文类型：文本、选区、图片、音频、图表或词典。
- 最大输入长度、预计 token/时长、模型和费用提示。
- 结构化输出 schema 和失败降级方式。
- 是否产生持久记录，是否需要用户确认。
- 是否联网、上传媒体、写文件或调用外部工具。

## 二、P0：基础能力与安全边界

P0 是所有后续功能的前置条件。当前文本上下文、统一任务和状态边界已经完成，下一阶段应补齐多模态接口与可追溯结果。

### P0.1 统一媒体上下文

新增 `JixiaContext` 类型：

- `text`：全文、选区、段落、词典、测试题目。
- `image`：图片 URL、页面位置、alt、OCR 文本、视觉描述。
- `audio`：音频来源、语言、时长、转写片段和时间戳。
- `chart`：原始数据、图表类型、ECharts option 或 Mermaid DSL。

每个对象都保存 `sourceUrl`、`pageTitle`、`createdAt`、`contentHash` 和用户是否确认。

### P0.2 结构化任务协议

为总结、翻译、解释、OCR、转写、图表生成建立统一请求协议：

- `taskType`
- `context`
- `provider/model`
- `budget`
- `outputSchema`
- `allowNetwork`
- `allowPersistence`
- `retryPolicy`

模型输出必须先解析和校验，再进入 UI；失败时显示可读文本或原始片段，不直接渲染未知 HTML/SVG。

### P0.3 隐私和权限

- 音频和图片上传前提示范围、目标服务和预计大小。
- API Key、Cookie、本地文件和浏览器权限不进入 prompt。
- 本地模型、云端模型和第三方工具分开显示。
- 对录音、语音克隆、图像生成和外部 Agent 设置显式开关。
- 媒体任务默认不持久化原始文件，只保存必要的文本结果和来源。

### P0.4 多模态能力边界（补充设计）

图片能力不应只做 OCR，而应拆成三条不同链路：

- **视觉理解**：图片描述、页面/截图问答、公式/表格/图表解释。优先使用支持视觉输入的模型，OCR 作为模型不可用时的降级路径。
- **OCR**：提取可复制文字、保留区域坐标和置信提示；结果可进入翻译、词典、测试和 Chat。
- **图像生成**：根据文章或用户确认的提示词生成示意图、信息图或配图候选；默认不宣称是真实证据，保存 prompt、模型、时间和来源声明。

三者都通过 `JixiaContext` 和 `JixiaTask`，但权限不同：视觉理解需要媒体上传权限，OCR 可选择本地处理，图像生成需要单独的生成权限和持久化确认。原始媒体默认只驻留内存，不进入历史记录。

音频同样拆开：浏览器 SpeechSynthesis 朗读属于本地低风险能力；音频转写需要上传或本地模型，复杂度和权限都高一级；语音生成/克隆属于后续实验能力，不进入 P0。

前期固定使用免费的 **GLM-4V-Flash** 作为图片视觉理解和 OCR 模型；插件在稷下设置中为它单独保存 API Key，不与文本模型 Key 混用。GLM-4V-Flash 先支持单图 Base64 输入，适用于图片描述、图片问答、图表初步理解和 OCR；多图、视频和其他视觉模型留作后续扩展。官方说明：[GLM-4V-Flash](https://docs.bigmodel.cn/cn/guide/models/free/glm-4v-flash)。

前期实现顺序固定为：GLM-4V-Flash 图片识别/OCR > 本地浏览器 SpeechSynthesis 朗读。音频转写、云端 TTS、图像生成和语音生成只保留设计，不进入前期实现。多模态供应商适配应集中在请求层，不在每个模块里复制 provider-specific payload。

后续模型候选：GLM-4V-Plus（多图/视频）、OpenAI 视觉模型、Gemini 视觉模型、Qwen-VL 和 Claude 视觉模型；后续只增加适配器，不改变 `JixiaContext` 与 `JixiaTask` 接口。图像生成候选包括智谱 GLM-Image、OpenAI Images 和其他供应商的图像生成模型，但必须单独处理费用、版权、来源声明和用户确认。

### 后续：统一全文正文筛选

当前所有模块必须通过同一个 `full_article` 上下文获取全文；朗读、总结、测试、翻译和词汇复习不得各自从 DOM 重新抓取。广告、导航、推荐、评论、页脚和重复文本的识别与过滤，后续作为独立章节实现，并形成可测试的正文筛选器；在该筛选器完成前，保持现有全文获取结果作为唯一来源。

## P0 补充设计：图像证据上下文

### 设计结论

图片不能只作为“已选择文件”保存在页面状态中。当前 Chat 只发送文本，因此会出现“界面提示已加入上下文，但模型没有收到图片”的问题。后续必须把图片建模为可追踪的 `MediaEvidence`，并明确区分：原始图片、视觉识别结果、用户是否确认发送、哪些模块使用了该结果。

```text
用户图片
  ↓ 用户确认
GLM-4V-Flash 单图/多图识别
  ↓
MediaEvidence：缩略图 + OCR/视觉结果 + 来源 + 时间 + hash
  ↓ 用户选择
仅识别结果 / 图片+识别结果 / 图片+文本 / 仅文本
  ↓
Chat / 选区解释 / 测试 / 翻译 / 词汇复习
```

### 数据结构

```js
{
  id: "media-...",
  kind: "image",
  source: "upload|page_image|selection|full_article",
  sourceUrl: "...",
  pageTitle: "...",
  alt: "...",
  thumbnailDataUrl: "...",       // 仅当前编辑上下文，默认不进入历史
  contentHash: "...",
  width: 0,
  height: 0,
  confirmed: true,
  recognition: {
    model: "glm-4v-flash",
    status: "pending|completed|failed|skipped",
    text: "OCR 和视觉说明",
    ocrText: "逐行文字",
    createdAt: 0,
    durationMs: 0,
    error: ""
  }
}
```

Chat 或其他模块的请求上下文增加：

```js
{
  textContext: { source: "selection|full_article|paragraph", text: "..." },
  mediaEvidence: [/* MediaEvidence[] */],
  mediaMode: "none|recognition_only|image_and_recognition",
  provenance: [
    { type: "text", label: "选中文本", source: "selection" },
    { type: "image_recognition", label: "图片 1 识别结果", mediaId: "media-..." }
  ]
}
```

### 三种用户流程

#### A. 上传图片，直接识别

1. 用户点击“图片”并选择一张或多张图片。
2. 立即显示缩略图、文件名、数量和预计处理提示。
3. 弹窗明确目标模型为 `GLM-4V-Flash`、图片数量、可能耗时和是否上传。
4. 用户确认后自动执行识别。
5. 进入独立“图片识别”结果视图，显示每张图片的 OCR 文本和视觉说明。
6. 结果可复制、重试、删除或“带结果进入 Chat”。

该流程不自动发送普通 Chat 问题，避免用户误以为图片已经进入对话。

#### B. 图片 + 识别结果进入 Chat

1. 图片缩略图显示在 Chat 输入框上方或输入框内的附件区。
2. 图片完成识别后显示识别结果摘要。
3. 用户可以继续输入问题。
4. 输入框中同时存在：图片附件、识别结果文本、用户问题。
5. 每个图片附件都有红色 `×`，可单独删除。
6. 发送时根据 `mediaMode` 选择：
   - `recognition_only`：只发送识别结果文本，不发送原图。
   - `image_and_recognition`：发送原图和识别结果文本。
   - `none`：只发送文本。
7. Chat 消息中明确标识：`图片 1 识别结果`、`用户文本`，避免模型误把 OCR 内容当成用户原话。

#### C. 网页选区/全文中包含图片

选区或全文上下文发现图片后，不自动上传，先弹出确认：

```text
发现 3 张图片。
将先加入图像工作区；你点击“发送勾选图片识别”后，才会使用 GLM-4V-Flash 串行识别，并把勾选图片发送给智谱 AI。

[加入图像工作区] [只使用文本] [取消]
```

确认后：

- 图片先进入图像工作区，以缩略图列表显示，默认勾选；用户点击“发送勾选图片识别”后才逐图上传到 GLM-4V-Flash。
- `Chat / 解释 / 翻译 / 词汇复习`：只合并已经完成识别的图片结果；待识别和失败图片保留在工作区，不伪装成有效上下文。
- `测试`：识别结果作为补充材料，题目必须标注“依据：正文”或“依据：图片 2 识别结果”。
- 用户选择“只使用文本”时，整条任务不得上传图片。

多图必须逐张建立 `MediaEvidence`，显示 `1/3、2/3、3/3` 的状态；允许单张失败后继续处理其他图片，并在结果中保留失败原因。发现数量不设硬上限，全部进入工作区；界面建议每次勾选不超过 10 张，以免等待时间过长。若本次发送超过 10 张，弹窗确认：确认后继续串行发送，取消则停止本次发送并保留勾选状态。识别成功后自动取消该图勾选，并显示“已处理”标记；用户仍可再次手动勾选重跑。图像工作区采用左图右结果的紧凑卡片，底部操作栏固定且高度压缩，方便随时发送、加入 Chat 或打开历史。底部提供“全选”复选框：勾选后选中所有图片，取消后清空所有选择；单图选择变化会同步全选或半选状态。

截图能力有两种入口：

- 主动截图：用户点击“截图网页”，稷下浮层临时隐藏，进入网页区域框选模式；确认后截图进入图像工作区并默认勾选。浏览器 Side Panel 不在网页截图范围内，稷下浮层也不会出现在截图中。
- 兜底截图：图片链接识别失败、下载失败时，系统可截取当前网页视窗作为兜底；兜底结果同样进入 `MediaEvidence`，并标记 `delivery: "screenshot"`。当前版本截取当前视窗，后续再补目标图片区域的滚动定位和精确裁剪。

### 任务模块规则

| 当前模块 | 文本 | 图片识别结果 | 原图 | 默认行为 |
|---|---:|---:|---:|---|
| Chat | 可选 | 可选 | 可选 | 先确认后由用户选择 |
| 选区解释 | 必须 | 可选 | 可选 | 文本和图片分别标注 |
| 测试 | 必须或选区 | 可选 | 默认不重复上传 | 图片结果只作为证据补充 |
| 翻译 | 必须 | 可选 | 默认不发送 | 翻译 OCR 文本 |
| 词汇复习 | 必须 | 可选 | 默认不发送 | 从 OCR 文本提取词汇 |

### 重要交互状态

```text
未选择
  → 已选择未确认
  → 已确认待识别
  → 识别中（单张/多张进度）
  → 已完成，可加入 Chat
  → 部分失败，可重试/删除单张
```

“已加入上下文”只能表示图片进入本地编辑上下文，不能表示已经发送给模型。只有识别请求真正成功后才显示“已识别”，只有 Chat 请求成功后才显示“已发送”。

### 隐私、成本和持久化

- 上传前必须显示模型、目标服务商、图片数量和预计耗时。
- 原始图片默认只保存在当前编辑上下文，不进入历史记录。
- 历史记录默认保存识别文本、模型、时间、来源和内容 hash，不保存原图。
- 用户明确勾选“保存原图”后才允许持久化，并需要单独的删除入口。
- 多图任务按图片数量提示时间和潜在费用；即使模型免费，也提示并发和等待成本。
- API Key、Cookie、网页隐私数据不能出现在识别结果 prompt 中。

### 前期实现顺序

1. 修复上传图片后真正调用 GLM-4V-Flash，并提供独立图片识别结果页。
2. 实现 Chat 输入框的缩略图、识别结果、删除和 `mediaMode` 选择。
3. 实现选区/全文图片发现、数量提示、用户确认、图像工作区勾选队列和多图进度。
4. 将同一套 `MediaEvidence` 接入解释、测试、翻译和词汇复习。
5. 最后再考虑网页图片自动发现、图片历史和原图持久化。

### 模型能力与图片发送边界（最终澄清）

“用户使用 AI 即允许外发”不能推导出“所有请求都应上传原图”。产品仍需告诉用户数据发送给哪个服务，并遵循最小发送原则；但不再把隐私做成阻塞式复杂流程。前期只需要：明确目标模型、在图片首次发送前确认、允许用户选择“只发送识别结果”或“原图+识别结果”。

必须把模型能力注册为显式能力，而不是只看服务商名称：

```js
{
  provider: "chatglm",
  model: "glm-5.2",
  capabilities: { text: true, vision: false, audio: false, imageGeneration: false }
}
```

当前文本 LLM（例如 `chatglm/glm-5.2`）不能因为同属智谱服务就被认为能够看图。`GLM-4V-Flash` 是独立的视觉理解模型，前期作为专用识别服务使用；它负责图片 OCR/视觉说明，不自动等同于当前 Chat 模型。

因此最终请求策略如下：

| 当前对话模型 | 图片识别服务 | 发给当前 LLM 的内容 | 是否发送原图 |
|---|---|---|---|
| 纯文本 LLM | GLM-4V-Flash | 用户文本 + GLM 识别结果 | 不发送，除非以后接入视觉模型 |
| 支持视觉的 LLM | 可选 GLM-4V-Flash | 用户文本 + 识别结果 | 默认不重复发送，可由用户开启 |
| 没有识别 Key | 无 | 用户可见图片和错误提示 | 不发送，不能假装已识别 |

图像模块的默认流程是：

```text
原图 → GLM-4V-Flash → 用户可见的 OCR/视觉结果
                         ↓
                 用户点击“添加到 Chat”
                         ↓
       当前 Chat LLM 收到识别结果文本和来源标注
```

这意味着你的理解在当前前期架构下是正确的：如果当前 Chat 选择的是纯文本模型，那么把原图直接放进 Chat 请求没有意义；应显示图片和识别内容给用户，真正发送给当前 LLM 的是识别结果。只有当用户选择了明确声明 `vision: true` 的模型时，才开放“原图+识别结果”发送模式。

还需要澄清：各家 API 并不都是“纯 LLM + 自动工具调用”。通常存在三种情况：

1. 纯文本 Chat Completions：只接受文本。
2. 多模态 Chat 模型：同一请求接受文本和图片/音频。
3. 独立视觉、OCR、音频或图像生成服务：由应用自行编排，或由 Agent/工具层显式调用；不会因为调用了普通文本 LLM 就自动完成图像识别。

稷下前期采用第 3 种显式编排：GLM-4V-Flash 识别 → 结果进入当前文本 LLM。后续接入真正的视觉 Chat 模型时，再根据能力注册切换到第 2 种。

### 多图识别与并发策略

当前前期视觉识别固定使用免费的 GLM-4V-Flash。该模型按单图识别设计，不能把“多张图片”直接假设为一次请求；多图任务采用串行队列：

```text
图片 1 → 识别 → 保存结果
图片 2 → 识别 → 保存结果
图片 3 → 识别 → 保存结果
```

界面显示 `1/3、2/3、3/3` 进度，单张失败不阻塞后续图片，并允许单张重试。这样可以控制请求并发、避免触发免费模型限流，也能让用户看到每张图片的独立结果。GLM-4V-Flash 是否允许并发，取决于账号等级和实时限流，不把并发作为产品前提。

后续接入真正支持多图的视觉 Chat 模型时，能力注册增加。这里的字段必须来自适配器/官方模型配置，不能仅凭模型名称猜测：

```js
{
  vision: true,
  maxImagesPerRequest: 5,
  supportsBatchVision: true,
  supportsParallelVision: false,
  maxConcurrentVisionRequests: 1,
  preferredImageStrategy: "single_request|serial|parallel",
  requiresImageDataUrl: true
}
```

路由规则（按以下顺序执行）：

1. 用户选择“仅识别结果”时，所有图片先交给独立视觉/OCR 编排器，Chat 只收到带图片编号和来源的识别文本。
2. 当前模型声明 `vision=true` 且 `supportsBatchVision=true`，并且数量不超过 `maxImagesPerRequest`：单请求发送多图和文本，保留图片顺序、编号和每图结果边界。
3. 模型声明支持视觉但不支持多图，或图片数量超过单请求上限：按图片串行发送；若声明允许并发，则使用 `maxConcurrentVisionRequests` 限制并发数，禁止无限并发。
4. 模型声明 `vision=true` 但没有明确声明批量/并发能力：保守按串行处理。
5. 纯文本模型：所有图片先串行交给 GLM-4V-Flash，再把合并后的识别结果发送给文本 LLM。

`preferredImageStrategy` 只是默认策略，不得覆盖安全上限、模型硬限制或用户选择。任何单请求失败都必须按适配器声明的降级策略拆成串行请求重试一次；并发请求发生限流（429）、超时或部分失败时，保留已完成结果并将失败图片回退到串行队列。界面必须显示实际采用的策略：`单请求多图`、`串行逐图` 或 `受限并发`，以及 `已完成/总数`。

这三种策略的产品语义如下：

- **单请求多图**：模型一次看到整组图片，适合需要跨图比较、排序、合并回答的任务；必须保留图片顺序。
- **串行逐图**：每张图片独立请求，结果实时返回，适合当前 GLM-4V-Flash 和未知能力模型。
- **受限并发**：多个独立请求同时进行，仅在模型明确支持并发且账号限流允许时启用；默认并发数为 1，需由适配器声明上限。

当前实现状态：GLM-4V-Flash 仍固定采用“串行逐图”。网页发现会把全部候选图片加入图像工作区，不设 8 张硬上限；每张图片默认勾选，用户点击“发送勾选图片识别”后按队列处理。已实现 `1/N` 进度、单图失败后继续、失败原因保留、逐图历史记录、完成后自动取消勾选、已处理标记、全选/半选状态和结果合并到 Chat。Chat 输入框现在可以直接上传图片或从工作区选择图片；视觉模型可以绕过 GLM-4V-Flash 直接发送原图，纯文本模型仍使用 GLM 识别结果。未来新增视觉 Chat 模型时，先补能力声明和适配器测试，再开放对应策略；未完成声明验证前，不得直接启用原生多图请求。

这里要区分两种“多图”：当前已经完成的是插件层的“逐张串行识别”；未完成的是模型层的“单次请求原生多图理解/跨图比较”，以及视频文件输入。两者不重复。

### 图片存储策略

- 当前工作区：原图只保存在页面内存，关闭页面后消失。
- 识别历史：当前使用 `chrome.storage.local` 保存 Data URL、识别结果、模型和时间，不写入插件安装目录。
- 后续优化：历史默认保存压缩缩略图和识别结果；原图只有在用户明确选择“保存原图”时才进入 IndexedDB，并提供删除入口。
- 不保存本地文件路径作为主要恢复方式，因为浏览器不会提供可靠、长期可访问的本地路径，原文件移动或删除后路径也会失效。

### 图像历史清理与导出

存储不能依赖用户清理浏览器缓存来管理。插件需要提供独立的图像历史管理：

- 按时间快速清理：一周前、四周前、六个月前、一年前。
- 自定义日期清理。
- 清理前显示数量和预计释放空间。
- 清理原图时保留或同时删除识别文本，由用户选择。
- 支持导出单条或批量识别记录。

导出格式：

```text
导出目录/
├─ image-name.png
└─ image-name.txt
```

TXT 至少包含：图片名称、来源、识别模型、识别时间、OCR 文本、视觉说明和内容 hash。浏览器扩展不能可靠获取或恢复用户电脑上的原始文件路径，因此导出必须生成新的图片文件和同名 TXT；不把本地路径当作恢复机制。

`chrome.storage.local` 和 IndexedDB 都不应被宣传为永久云端存储：卸载扩展、清除扩展数据、浏览器配置清理或存储配额不足都可能导致数据丢失。历史 UI 应显示“本地存储”，并提供导出和清理入口。

## 三、P1：直接提升阅读和无障碍体验

P1 选择低风险、高频、能立即复用当前网页上下文的功能。

### P1.1 选区解释独立结果视图

输入：选区文本、前后段落、页面标题。

输出：简释、术语、翻译、上下文作用、例句、原文定位。

交互：解释 -> 追问 -> 加入词典 -> 生成复习卡 -> 回到 Chat。

### P1.2 朗读与文本转语音

先使用浏览器 SpeechSynthesis 或配置的 TTS 服务，统一封装为 `audioSpeak` 任务。

- 支持当前选区、段落、总结、题目解析。
- 支持暂停、继续、语速和语言切换。
- 文本按段落切片，避免一次性生成超长音频。
- 记录播放位置，方便继续学习。

### P1.3 音频转写

先支持用户主动选择的音频文件或页面媒体，使用 Whisper 类能力转写。

- 输出带时间戳的段落。
- 转写结果进入全文上下文，可总结、测试、提取词汇。
- 明确语言和转写不确定处。
- 不默认监听网页或后台录音。

### P1.4 图片说明和 OCR

- 图片右键/悬浮入口：生成简洁描述、详细描述或提取文字。
- OCR 文本可复制、翻译、加入词典。
- 对公式、表格和图表分别标注“识别结果”和“模型解释”。
- 失败时保留原图，不生成虚假的确定性描述。

### P1.5 可访问性结果

所有媒体结果都提供：键盘操作、屏幕阅读器文本、复制纯文本、原文回看、错误提示和重新生成。

## 四、P2：学习闭环与可编辑可视化

P2 开始把“生成一次”变成“可复习、可编辑、可追踪”。

### P2.1 词汇复习与掌握度

数据来源：文章词典、选区解释、测试错题、音频转写。

逻辑：

1. 合并词条并去重。
2. 根据出现频率、用户错误和最近复习时间排序。
3. 生成选择、填空、词性判断和听辨题。
4. 保存每个词条的正确率、连续正确次数和下次复习时间。
5. 后续再引入 BKT 或间隔重复算法。

### P2.2 结构阅读

输出结构化 JSON：

- 主旨
- 章节/段落层级
- 论点
- 证据
- 因果关系
- 反例/争议
- 待验证说法

每个节点必须绑定原文段落或媒体时间点。结构阅读结果可以进一步渲染为列表、Mermaid 思维导图或时间线。

### P2.3 泛化图表能力（图表能力）

图表能力不是“技术图生成器”，而是把信息转换为可理解、可编辑、可导出的视觉表达。架构图只是其中一个领域模板。参考 `tt-a1i/archify` 的重点是视觉表达管线、主题化预览和多格式导出，而不是复制其 Skill 或限定其架构语义。

目标范围：

- 结构与关系：思维导图、概念网络、分类层级、实体关系、论点—证据图。
- 过程与变化：流程图、决策树、时间线、学习路径、状态转换、因果链。
- 比较与数据：表格、柱状/折线/散点图、占比图、雷达图、矩阵和趋势摘要。
- 空间与计划：路线/地点关系、项目排期、资源分配、二维布局；地图和精确地理数据需要单独的来源与权限约束。
- 表达与无障碍：信息图、讲解卡片、图表文字化摘要、可供朗读的图表说明。

统一数据流：

```text
文本 / 表格 / 图片识别结果 / 用户数据
              ↓
     图表意图 + 推荐类型
              ↓
  ChartModel（节点、边、系列、单位、来源）
              ↓
     schema / 数据 / 事实校验
              ↓
  HTML/SVG/Canvas/Mermaid/ECharts 渲染
              ↓
      预览、编辑、导出、复用
```

统一结果至少包含 `intent`、`chartType`、`data`、`layout`、`theme`、`provenance`、`confidence` 和 `editableSource`。`editableSource` 可以是 Mermaid DSL、ECharts option、HTML/SVG 或内部 JSON，但不能只保存 PNG。用户编辑后要区分“模型生成”“用户修改”和“来源数据”，避免重新生成覆盖人工修订。

验收标准：

1. 图表类型按表达目的推荐，允许用户手工切换；不因输入属于技术文章就默认生成架构图。
2. 数据图表必须显示单位、时间范围、缺失值和来源；没有数值时不得伪造坐标或趋势。
3. 节点和边应能回到原文段落、图片识别结果、测试记录或用户输入。
4. 先生成结构化 `ChartModel`，再生成渲染 DSL；DSL 解析失败时降级为列表/表格。
5. 预览支持主题切换、缩放、复制可编辑源、重新生成和 PNG/SVG 等导出。
6. 图表必须有文本摘要和键盘可达的替代内容；低视力用户可使用放大、朗读或数据表视图。

`chart` 不只是输出类型，也可以成为可引用的 `JixiaContext`：保存原始数据、图表模型、渲染版本、来源和用户确认状态。Chat、结构阅读、测试、复习和未来的学习书都可以消费同一份图表上下文。

### P2.4 文章配图辅助

- 为文章生成“配图说明候选”，由用户确认后再生成。
- 图像生成只产生示意图，不替代文章事实来源。
- 记录 prompt、模型、生成时间和来源声明。
- 对学术或新闻内容默认优先生成图表/结构图，而不是生成写实图片。

## 五、P3：研究型和高级 Agent 能力

P3 用于扩大稷下的研究和创作能力，必须建立在 P0-P2 的证据、权限和历史结构之上。

### P3.1 多视角深度研究

借鉴 STORM：先提出研究问题和大纲，再检索资料、收集证据、生成报告。用户可以暂停、删改问题、限定来源和预算。

### P3.2 学术资料工作区

借鉴 PaperQA：支持 PDF/网页/笔记的引用型问答、证据重排、矛盾检测和来源质量提示。

### P3.3 交互式学习书

借鉴 DeepTutor Book：把文章和词典编译为章节、摘要、测验、闪卡、图表和笔记块。每个块都可重新生成、移动、编辑和追溯来源。

### P3.4 角色化 Agent 和 Skill

- 阅读教练：提问和追问，不直接给答案。
- 研究助手：检索、引用和事实核查。
- 语言教练：转写、发音、翻译和跟读。
- 写作助手：提纲、草稿、引用卡片和修改 diff。

每个角色通过受限 Skill 描述输入、输出、工具权限和验收标准；不允许 Skill 默认执行任意命令或读取全部本地文件。

### P3.5 音频/图像生成进阶

- 章节播客和多角色讲解。
- 个性化语速、语言和方言练习。
- 基于文章结构的可编辑信息图。
- 低视力用户的图表音频化描述。

这些能力需要额外的成本、版权、声音授权和事实准确性设计，应在明确的实验开关后开放。

## 六、推荐实施顺序

1. P0：补齐多模态 Context、Task schema、权限和结果引用。
2. P1：朗读、音频转写、图片 OCR/描述、选区解释独立视图。
3. P2：词汇掌握度、结构阅读、泛化图表能力与可编辑视觉结果（Mermaid/ECharts/HTML-SVG 作为渲染后端，而不是产品边界）。
4. P3：学术研究、交互式学习书、角色 Agent、音频/图像生成进阶。

每个阶段都应遵循同一验收标准：

- 输入来源明确。
- 结果可以回到原文/媒体位置。
- 输出经过 schema/语法校验。
- 失败时可降级为纯文本。
- 用户知道是否上传、保存、联网和产生费用。
- 功能可以被键盘和屏幕阅读器操作。
